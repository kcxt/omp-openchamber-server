# R4: `fork` (and `branch`) output

Tests: `test/contract/tree.test.ts` "R4 fork and branch" (both binaries).

## Source

`rpc-mode.ts` `case "fork"` (~2198) shares the session-change path with `new_session`/`switch_session`/`branch`: fork refuses while `isBusyForSnapshot` (`session_busy`), then `session.fork(entryId, {requireIdle:true})`; the response is just `{cancelled:false}`. `handleRpcSessionChange` (`rpc-mode.ts` ~955) clears the subagent registry on success.

## Recorded behaviour (real omp, fork at `a2` of `u1 a1 u2 a2 u3 a3`)

- The child switches onto the new transcript: `get_state.sessionFile` and `sessionId` change; the response carries no path, so read `get_state.sessionFile` after the call. The file lives in the same bucket directory as the parent, named `<timestamp>_<new uuid>.jsonl`.
- File content: line 1 is the 256-byte `title` slot, line 2 the header `{type:"session", version:3, id:<new>, timestamp, cwd:<same cwd>, parentSession:<parent's file path>}`. **`parentSession` is the parent's absolute file path, not its id.** Entries are the root-to-target path **including** the target, with the **original ids and parentIds** preserved (`u1 a1 u2 a2`, parents `null u1 a1 u2`). No new bookkeeping entries were observed in a header-only fork.
- The parent file is byte-identical afterwards. `get_entries.leafId` in the fork is `a2`.
- The lease of the fork is held by the forking process at once (probe from a second child, `lease.test.ts`); the unwritten parent stayed unheld (a fork of a session whose process already holds the lease was not run).
- `branch {entryId: u2}` (fork before a user message): response `{text:"question 2", cancelled:false}`; new file holds `u1 a1` only, same header shape with `parentSession`. This is the existing "edit message" behaviour (text returns to the editor).
- `fork` while a run is live: `{success:false, code:"session_busy"}`.

## Versus the current sidecar fork-from-message

The sidecar copies the transcript itself (`forkOmpSession`); omp's own fork produces the same shape (copy of the active path, header with `parentSession`), so `fork` replaces it with these differences to handle: ids are preserved, so a `legacyMessageIds`/client-id map keyed by entry id carries over unchanged, but the new session id is omp's (uuidv7), and lineage is by path, so any code that resolves `parentSession` as an id must resolve it as a path (the header's `parentSession` is only lineage; just artifact sub-sessions are children).
