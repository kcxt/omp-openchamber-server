# R9: subagent wiring (PLAN §3.15)

Answered from the patched omp checkout `/hdd/brute/projects/oh-my-pi-local` (branch `local`). All paths are under `packages/coding-agent/src/`. Statements marked `[INFERENCE]` were read, not run.

## 1. Is the `subagent_event` payload complete enough for a TurnTranslator?

**Yes for the live stream; it is unfiltered and starts before the first prompt. It is lossy for anything that happened before the host subscribed.**

- Payload: `{ id, event }` where `event` is the child's full `AgentSessionEvent` (`task/types.ts:35-41`). The wire def is `SubagentEventPayload { id: string; event: RpcAgentEvent }` (`modes/rpc/wire/frames.ts:90`), the same event union a root session emits.
- Source: the executor's run monitor subscribes to the child session and publishes *every* event with no `isAgentEvent` filter: `session.subscribe(event => { emitSubagentEvent(event); … })` (`task/executor.ts:2329-2330`, `emitSubagentEvent` at `1835-1838`). The filtered `agentEventTypes` set (`executor.ts:262-277`) only drives progress bookkeeping, not this stream.
- Start of stream: `monitor.attach(session)` runs at `executor.ts:5346`, after `session_init` is appended (`5279`) and before skill autoload (`5350`) and the first `driveSessionToResult` prompt. So the assignment's own `message_start`/`message_end` (user), `agent_start`, `turn_*`, `message_update`, `tool_execution_*`, `agent_end` are all in the stream. `session_init` is a transcript entry, not an event; read it from the artifact file.
- Same bus path for follow-up turns, wakes and revivals: `attach` is called again for each (`executor.ts:3538`, `4062`, `4084`), publishing under the same `id`.
- RPC forwarding: `RpcSubagentRegistry.handleEvent` writes `{ type: "subagent_event", payload }` verbatim (`modes/rpc/rpc-subagents.ts:256-260`). Consequences for the translator:
  - Only emitted at `set_subagent_subscription { level: "events" }` (`rpc-subagents.ts:154-165`, `258`). Events before the level was set are not replayed. Set it once, right after the child starts, before the first prompt.
  - It bypasses `set_event_filter` and its `messageUpdates: "delta"` projection (`sessionEvents.setFilter` only wraps the root session's forwarder). `message_update` therefore arrives in **full** (accumulated snapshot) form, not delta. The root-session translator's delta path must not be assumed for children.
  - Dropped after `RpcSubagentRegistry.clear()` (new/switch/branch/fork) via `#staleSubagentIds` (`rpc-subagents.ts:143-152`, `257`).
  - Frames have no sequence number. Backfill with `get_subagent_messages { subagentId, fromByte }` (`rpc-subagents.ts:70-107`, `262-278`), which works for running and finished (retained, max 256) ids.
- Lifecycle for identity: `subagent_lifecycle` carries `sessionFile` (artifact path), `parentToolCallId`, `detached` (`rpc-subagents.ts:196-227`, payload built at `executor.ts:5248-5259`). The terminal lifecycle frame deletes the roster entry (`rpc-subagents.ts:219-221`) but keeps the id → sessionFile mapping.

Stub frames to record (shape from source): `{"type":"subagent_lifecycle","payload":{"id":"…","agent":"task","agentSource":"bundled","status":"started","sessionFile":"<parent>/<id>.jsonl","parentToolCallId":"…","index":0,"detached":false}}`, then `{"type":"subagent_event","payload":{"id":"…","event":{"type":"agent_start"}}}` … `{"type":"agent_end",…}`, then lifecycle `completed`.

## 2. Does `steer_subagent` work on a running async (background) task?

**Yes, identically to a sync one. There is no sync/async distinction in the path.**

- Async vs sync is only `detached`: `task/index.ts:1032-1036` (`detached = async enabled && job manager && !blocking`), `#launch({… detached: true })` at `1613-1619`, sync fan-out `detached: false` at `1843`. Both end in `runSubprocess`, which registers the child in `AgentRegistry` as a `sub` ref with `status: "running"` and a live session; `detached` only rides the lifecycle/progress payloads (`executor.ts:475-481`, `5252`).
- `handleRpcSteerSubagent` (`modes/rpc/rpc-mode.ts:840`) accepts any id for which `resolveOwnedLiveSubagent` (`rpc-subagents.ts:299-312`) finds: a roster snapshot in `pending`/`running` with a `sessionFile`, and an `AgentRegistry` ref of kind `sub`, status `running`, same `sessionFile`. Then `ensureLive` + `session.prompt(message, { streamingBehavior: "steer", throwOnDrop: true })`.
- Failure modes the sidecar must map: `Subagent not running: <id>` (unknown, finished/accepted, parked, aborted, or a snapshot still `pending` with no registry ref yet) and `Subagent refused the message: …` (prompt dropped by abort/disposal/preflight). A `pending` async child (queued behind the spawn semaphore, `task/index.ts:1640-1643`) is **not** steerable until it is `running`.
- Once the child finishes: ref goes `idle` (live) or `parked` before the terminal lifecycle frame; `steer_subagent` refuses (`status !== "running"`). The new `resume { subagentId }` (P5, `rpc-mode.ts` `handleRpcResume`) reaches finished-but-registered children via `ensureLive`, which answers PLAN §3.15's "unless R9 finds an RPC resume path": it does, for ids still in the registry or retained transcript map; a child of a *previous* process is not reachable (no ref).

## 3. What does `abort_and_restore_queue` do to running subagents?

Handler: `modes/rpc/rpc-mode.ts:2164-2172`: `session.clearQueue({ forInterrupt: true })`, `goalController.stopForHostAbort()`, `abortBuiltinCommands`, `await session.abort({ reason: USER_INTERRUPT_LABEL })`. `abort` and `abort_and_prompt` share the same `session.abort`. Nothing there names subagents.

- **Sync (blocking, inline) subagents: aborted, as part of aborting the parent turn.** `AgentSession.abort` calls `agent.abort(reason)` (`session/agent-session.ts:12258`), which cancels the in-flight `task` tool call. The sync fan-out runs each child under the tool call's signal: `#runSyncSpawns(… signal)` → `mapWithConcurrencyLimitAllSettled(…, signal)` → per-child `workerSignal` → `run.attach({ signal: workerSignal })` (`task/index.ts:1823-1863`). The executor turns that abort into `monitor.abortActiveSession()` (`task/executor.ts:5313-5325`). Result: the child's run ends `aborted`, the lifecycle frame goes `aborted`, `task` returns an aborted result. [INFERENCE] that the tool-call signal is the one `agent.abort` fires; the executor side is read directly.
- **Async (detached) subagents: NOT aborted.** Their `runSignal` comes from the `AsyncJobManager` job (`task/index.ts:1570`, `1620-1621`), not the parent tool call. `abort()` never calls `#cancelOwnAsyncJobs`; only `newSession` (`agent-session.ts:12351`), `switchSession` to a different session (`14265`), branch/fork paths (`14604`, `14733`), `/clear`-style reset (`7089`) and dispose (`6710`) do. So after `abort_and_restore_queue` a background task keeps running, keeps emitting `subagent_event`/`progress`, and its completion later wakes the parent (an async-result follow-up) unless that result is dropped by `#advisors.autoResumeSuppressed`-style latching: `abort` sets `autoResumeSuppressed` on a user interrupt that stopped something (`12207-12213`), which affects advisor/background auto-resume, not job lifetime. [INFERENCE] for the exact resume behaviour of a late async result; the non-cancellation is read directly.
- **Queued input**: `clearQueue({ forInterrupt: true })` withdraws user steering/follow-ups; messages for subagents (`steer_subagent` prompts) go to the child session's own queue and are untouched.
- **Sidecar consequences (§3.4/§3.15):** a Stop in OpenChamber on the root session must also issue `cancel_subagent` for each child the runtime's snapshot lists as running with `detached: true` if the user expects background work to stop; sync children stop with the parent. Because a stretch stays open while async work is pending (§3.1), after an abort with live async children the root session will *not* go idle until they finish or are cancelled. `statusOf(child)` must keep reading `get_subagents`, not the parent's abort.
