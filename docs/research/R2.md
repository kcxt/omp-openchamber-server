# R2: `get_entries{since}`, user-entry order, compaction

Tests: `test/contract/entries.test.ts` (both binaries). Pinned omp as in R1.

## Source

- `rpc-mode.ts` `case "get_entries"` (~2450) calls `selectRpcEntries(sessionManager.getEntries(), getLeafId(), since)` (`modes/rpc/rpc-compat.ts:14-25`): no `since` → every entry in append order; `since` → entries strictly after the matching id; an id that is not in the list → failure `{success:false, error:"Unknown entries cursor: <id>", code:"unknown_since"}`; `leafId` always passes through.
- `SessionManager.getEntries()` is the in-memory append list (`session/session-manager.ts`, `#recordEntry`); branches are not removed from it.

## Recorded behaviour (real omp, fixture transcript, then live turns)

- Fixture of 6 message entries: `get_entries` → ids in file order, `leafId` = last id; `since:u2` → `[a2,u3,a3]`; `since:a3` → `[]` with `leafId`; `since:"nope"` → `unknown_since`.
- `unknown_since` happens for an id that is not in the **current session's** list: another session's entry id, or an id from before `new_session`/`fork`/`switch_session`. It does **not** happen across compaction: `compact` appends a `compaction` entry (`{summary, shortSummary, firstKeptEntryId, tokensBefore, details}`), the file keeps every old line, and `since:<id before the compaction>` returns the old tail plus the compaction entry. `get_messages` shrinks (first message becomes a `compactionSummary`), `get_entries` does not.
- **User entries are appended in delivery order, not acceptance order.** Run: prompt `SLOWRUN start`, then `follow_up "FOLLOWUP accepted first"`, then `steer "STEER accepted second"` mid-stream. Transcript order and `message_start:user` frame order are `start, STEER, FOLLOWUP`: the steer is delivered at the next turn boundary, the follow-up only once the model has nothing left to say. The journal around them also holds non-message entries (`custom date-cwd-reminder` before the first user message, `custom system-prompt-digest`, `custom_message async-result` wakes, `model_change`, `thinking_level_change`), so "the next N entries" is not "the next N user messages": filter by `type === "message" && message.role === "user"`.
- The steer user message carries `steering:true`; its text in the journal is the raw text, while the text sent to the model is wrapped in a `<system-notice>User interjection…` prefix (observed in the provider request, not in the journal).
- Message frames carry `messageId` (`msg-1`, `msg-2`, … unique per omp process, shared by `message_start`/`message_update`/`message_end` of one message). The user `message` object has **no `id`** field; `events.ts` 11c reads `message.id` for `ompMessageId` and gets `undefined` today. The frame-level `messageId` is the available handle until P1 lands.

## Transcript file lifecycle (affects "since" cursors and lease probes)

- A fresh process reports `get_state.sessionFile` (a path) but the file does **not exist** until the history contains an assistant message (`#shouldHaveSessionFile`, `session-manager.ts:1668`: `forceFileCreation || fileIsCurrent || historyContainsAssistantMessage`). `set_model`, `set_thinking_level` and the user message are held in memory until then and written with the first assistant message. No lease is held before that (R6).
- `new_session`, `fork`, `branch` and `switch_session` to a **missing path** force file creation (header-only for new/switch); `new_session`, `fork` and the missing-path switch also take the lease immediately (probed; `branch` lease not probed).
- `set_model` journals `{type:"model_change", model:"<provider>/<id>", role:"default", resolvedModelIsFallback:false}` (`session/model-controls.ts:325` → `SessionManager.appendModelChange`, `session-manager.ts:3717`); `set_thinking_level` journals `{type:"thinking_level_change", thinkingLevel, configured}` only when the effective level changes (`model-controls.ts:603`, `appendThinkingLevelChange`, `session-manager.ts:3688`); the level is clamped to the model (a non-reasoning model stays `off`).
- **A record without an `id` is not skipped.** Appending `{"type":"oc_notice"}` to a transcript makes omp load it as an entry with no id: `get_entries.leafId` is absent, `get_messages` is empty, `messageCount` 0. A foreign record that does carry `id`/`parentId: <leaf>` extends the branch harmlessly (leaf becomes its id, history intact). This confirms the sidecar-records rule.

## Findings that contradict PLAN.md

- §3.7 fallback ("record client ids per stretch in order, pair them with the new user entries from `get_entries{since}`") is wrong whenever a steer and a follow-up are both pending: pair by content (the raw text is in the entry, minus the steer wrapper in the model request only), or wait for P1.
- §3.7 says `TranscriptReader` uses `hostMessageId`; until P1, `message.id` does not exist on user messages in `message_start` frames either.
