# R1: frame order of an activity stretch

Pinned omp: `oh-my-pi-local` (branch `local`, upstream dca23990ad + kept patches; line numbers are for the working tree at 430ac42928 and drift as P1–P5 land, so function names are given too). Recorded 2026-11-22 with `CONTRACT_OMP=real` against the scripted fake provider; the asserting tests are `test/contract/stretch.test.ts` (11 tests, pass on both binaries).

## Source

- `RpcSessionSettleWatcher` (`modes/rpc/rpc-session-settle.ts:44-110`): `observe` marks the stretch active on `agent_start`, and on every terminal `agent_end` runs `check()`. `check()` waits two macrotasks (so the `prompt_result` frames written one macrotask after the yield land first), drains owner-scoped async work, and emits one `session_settled` when `isSessionSettled` holds. `markActive()` opens a stretch for a pending host-scheduled turn (goal continuation).
- `isSessionSettled` (`session/session-settle.ts`): `!isStreaming && !hasAdmittedSubmission && queuedMessageCount === 0 && !hasPendingAsyncWork() && scheduledTurn?.() !== true`.
- `RpcPromptResults` (`modes/rpc/rpc-prompt-results.ts:57-196`): a prompt dispatched as a fresh turn owns the first run that starts after it was accepted; a prompt queued into a live run reports at the first yield with the queue drained (`queuedMessageCount === 0`). The frame is written in `setImmediate` after the `agent_end`, and `sessionSettled` is read at that moment.
- `rpc-mode.ts`: `case "prompt"` (~2106), `steer`/`follow_up` (~2130, no ticket, so no `prompt_result`), `abort` (~2157), `abort_and_restore_queue` (~2164, `session.clearQueue({forInterrupt:true})` then `session.abort`), `abort_and_prompt` (~2175).

## Recorded frame orders (labels: `message_*` carry the role, deltas and `tool_execution_update` elided)

Plain turn:

```
response:prompt agent_start turn_start message_start:user message_end:user message_start:assistant message_end:assistant
turn_end agent_end prompt_result{agentInvoked:true,status:completed,sessionSettled:true} session_settled
```

Tool turn (`read`): one `agent_start`; two turns around the tool result:

```
response:prompt agent_start turn_start message_start:user message_end:user message_start:assistant message_end:assistant
tool_execution_start tool_execution_end message_start:toolResult message_end:toolResult turn_end
turn_start message_start:assistant message_end:assistant turn_end agent_end prompt_result{…,true} session_settled
```

Follow-up queued with `prompt{streamingBehavior:"followUp"}` while the first turn streams (one stretch, one run, two `prompt_result`s after the single `agent_end`):

```
response:prompt agent_start turn_start message_start:user message_end:user message_start:assistant
queue_update{followUp:[…]} response:prompt message_end:assistant turn_end queue_update{[]}
turn_start message_start:user message_end:user message_start:assistant message_end:assistant turn_end
agent_end prompt_result(id1) prompt_result(id2) session_settled
```

The `follow_up` and `steer` commands behave the same except they answer with no data and own no `prompt_result`.

Steer while streaming: delivered at the next turn boundary inside the same run (`turn_end`, `queue_update`, `turn_start`, `message_start:user{steering:true}`); a steer that arrives while `bash` runs backgrounds the command ("Backgrounded early to handle an incoming message") and its completion later wakes the session (below). The steer text reaches the model wrapped in a `<system-notice>User interjection during work…` prefix.

Abort (`abort` with nothing queued): the response comes **after** `agent_end`:

```
… message_end:assistant(stopReason aborted) turn_end agent_end response:abort prompt_result{status:aborted,sessionSettled:true} session_settled
```

`abort` with a follow-up still queued **strands** the stretch: `agent_end`, `response:abort`, `prompt_result{status:aborted,sessionSettled:false}`, then nothing. `get_state` stays `{isStreaming:false,isSettled:false,queuedMessageCount:1}` and no `session_settled` follows (observed for 30 s). `abort_and_restore_queue` on the stranded session returns the item (`data.followUp:[{text}]`), clears the queue (`isSettled` true) but emits no `session_settled`; the follow-up's `prompt_result` is only reported by the next run that yields with the queue drained.

`abort_and_restore_queue` mid-run (follow-up + steer queued): response data `{steering:[{text}], followUp:[{text}]}`; one run; `prompt_result{aborted,sessionSettled:true}` for the running prompt and for the queued prompt; one `session_settled`; the queued text is never delivered.

`abort_and_prompt`: `agent_end`, `response:abort_and_prompt`, new `agent_start` (message_start:user for the replacement), `prompt_result(old){aborted,sessionSettled:false}`, replacement frames, `agent_end`, `prompt_result(new){completed,true}`, one `session_settled`.

Background work wakes inside the stretch. `bash{async:true}` (and the `task` tool) return at once; the run yields with `prompt_result{sessionSettled:false}`; when the job finishes the session wakes itself (`agent_start turn_start message_start:custom message_end:custom message_start:assistant … agent_end`) and only then `session_settled` is written, once:

```
… agent_end prompt_result{sessionSettled:false} agent_start turn_start message_start:custom message_end:custom
message_start:assistant message_end:assistant turn_end agent_end session_settled
```

The wake appends a `custom_message` entry (`customType:"async-result"`) to the transcript.

Local commands (empty input; builtins such as `/move`): the `prompt` response itself carries `data:{agentInvoked:false}`, no `prompt_result`, no stretch (`command_output` frames precede the response).

## Findings that contradict PLAN.md assumptions

1. **`abort` is not enough with queued input.** PLAN §3.4 step 2 uses `abort_and_restore_queue`, which is right, but any other `abort` path (host abort on a runtime that does not know about the queue, the deadline path) leaves a stretch that never settles. The runtime must treat "aborted with `queuedMessageCount > 0`" as unsettled and call `abort_and_restore_queue` (or clear the queue) rather than wait for `session_settled`.
2. **`abort_and_restore_queue` on an already-idle (stranded) session emits no `session_settled`.** The "wait for `session_settled` or `prompt_result{sessionSettled:true}` bounded by the deadline" rule of §3.4 needs the `get_state.isSettled` check as a third exit.
3. The abort response arrives after `agent_end`, not before; PLAN's "prompt promise resolves on acceptance" is unaffected, but an abort request must not time out at the 5 s deadline merely because the run is slow to yield.
4. Each queued prompt gets its own `prompt_result`, all after the single `agent_end` (steer/follow_up commands get none).
